# Maintainer compute publication

Maintainers publish exact retained image candidates and their source inventories.
Organization operators consume the resulting public catalog; they do not sign
inventories or publish images. The guided command requires Python and GitHub CLI,
not local Docker access. GitHub-hosted publication and catalog verification use
Docker and Skopeo, without rebuilding the retained images.
Candidates must contain the approved public Noether revision documented in
[images](images.md). A different Noether source revision is refused before source
upload or signing; build a matching image and corresponding source bundle.

```sh
make compute-publish
```

Select the retained candidate handoff when prompted. The wizard discovers
hash-bound Spaces upload receipts, verifies the candidate against authenticated
successful CI evidence, and produces signed **observed-source provenance** from
the actual image SBOM and retained source collection. Every observed component
must have matching identity/version evidence and existing source/notice
candidates. Missing paths, versions or explicit unresolved technical materials
block publication. No component-by-component JSON editing is required.

The signed format is `format: 2`, purpose `observed-source-provenance-v1`.
Its component disposition is `observed-source-candidates`, not a claim of
verified corresponding-source completeness. Generic inventory/closure caveats
remain visible and signed. `human_review_verified`, `legal_audit_verified`, and
`complete_dependency_closure_verified` stay false. This is a signed provenance
and distribution decision, **not** a fabricated human review or legal audit.

The CLI rechecks the exact archive, recipe, source bundle and component inventory
before prompting privately for a signing passphrase. Key creation and trust-key
enrollment require separate confirmations; private keys remain encrypted and
owner-only. Public source distribution, registry distribution and hosted Actions
costs are confirmed in the CLI. Secrets never become argv or public artifacts.
Preserve the private publication journal when retrying; inputs and dispatch/run
identities are retained rather than silently repeated after an uncertain reply.

The public attestations and enrolled key are placed on isolated publication
branches. `compute-publish.yml` copies each original candidate to GHCR, verifies
anonymous source delivery, pulls the exact public digest, and runs real worker
acceptance. GHCR packages may need a one-time owner action to change visibility
to **Public**; a successful private push is not a completed publication. Resume
the same CLI state after making that change. `compute-combine.yml` then repeats
anonymous source/digest/pull/execution checks and binds the completed catalog to
the selected successful publication run IDs. Modal remains a separate operator
step, `make compute-setup`; publication never enables a paid compute relay.

The exact `recipe.tar` is retained in each source bundle and hash-bound by the
attestation. Before signing, the guided CLI reconstructs the unsigned archive
recipe and compares its exact file set and Git blob hashes with the authenticated
successful candidate commit/tree on GitHub. That original commit/tree must remain
obtainable in the selected repository for this initial trust establishment; an
editable draft or archive revision label alone is not accepted as proof.
Hosted publication can reconstruct and check the signed recipe without
fetching a historical Git commit. CI provenance still names the original source
revision and successful candidate workflow; deleting Git history does not
change those recorded identities or justify substituting a rebuilt image.

The advanced commands below remain available for source delivery and explicit
human reviews. Format-1 human signatures use a separate purpose/domain and
remain verifiable; their approval flags are never generated by the machine path.

To host corresponding sources on GitHub, select an **already-public repository**
and an existing published, non-prerelease release. Review the entire bundle for
public distribution before invoking:

```sh
uv run python -m reasoning_ledger.image_review publish-source \
  --source-bundle /private/sources.tar --repository OWNER/PUBLIC-SOURCES \
  --release source-bundles-v1 --state /private/source-upload
```

The wizard shows the exact hash, byte length and retained file inventory, then
requires explicit public-distribution confirmation. It never creates a
repository, changes visibility, creates releases, or replaces existing assets.
Assets have digest-derived names; retries recheck existing anonymous bytes.
GitHub assets must be smaller than 2 GiB. Use DigitalOcean Spaces for larger
bundles.

## Public source delivery with DigitalOcean Spaces

Run the maintainer wizard without Docker or a Node build:

```sh
make compute-source-publish SOURCE_BUNDLE=/private/sources.tar
```

The wizard asks for a bucket and region, opens the DigitalOcean Spaces access-key
page if requested, and accepts the access key and secret through hidden prompts.
Enter the **Access Key ID** at the first hidden prompt and its matching
**Secret Key** at the second. Spaces credentials are separate from DigitalOcean
API tokens. Use a bucket-limited
Read/Write/Delete key for an existing bucket. Creating a bucket requires a
full-access Spaces key; revoke it or replace it with a limited key afterward.
DigitalOcean requires browser-based key creation. The command never stores keys
or passes them through command-line arguments. A noninteractive credential input
is an owner-only, mode-0600 JSON file containing `access_key` and `secret_key`:

```sh
uv run --locked --extra publication python -m reasoning_ledger.image_review \
  publish-source-spaces --source-bundle /private/sources.tar \
  --bucket reasoning-sources --region ams3 \
  --credentials-file /private/spaces-credentials.json
```

The `publication` extra supplies the S3 SDK; ordinary server and bot installations
do not need it. The source-upload inventory and multipart journal live under
`~/.reasoning-compute-publication`, with separate private directories for each
bundle SHA-256. `SOURCE_BUCKET`, `SOURCE_REGION` and `SOURCE_STATE` override the
Make command's prompts/defaults. The Python command supports the equivalent
`--bucket`, `--region` and `--state` options. Omitted source paths are prompted.
After a failed bucket creation or interrupted upload, rerun the same command with
the original source archive, bucket and region. Credentials are requested again;
correcting them does not change the retained publication intent. Keep the private
journal so the command can recheck bucket existence and resume its own upload.

Before any upload, confirm public distribution of the entire inventoried archive
and its storage/bandwidth charges. A missing bucket requires an additional paid
creation confirmation: the first Standard Spaces bucket can start a $5/month
subscription, with possible usage overages. The new bucket remains private;
only the selected object receives public-read access. Existing bucket policies,
ACLs, lifecycle rules and other objects are unchanged.

Object URLs use a SHA-256 namespace and a retained random upload key to isolate
concurrent publications. The command refuses to replace an existing object:
it verifies its anonymous bytes instead. This is not a provider object-lock
guarantee against other writers. Retrying the same inputs resumes only its own
retained multipart upload, skips rechecked acknowledged parts and recovers an
uncertain completion by hashing the actual public object. It never adopts or
aborts unrelated uploads. Preserve the journal after interruptions; do not
expire/delete published source objects while their releases require them.

Completion requires a fresh anonymous HTTPS download whose full SHA-256 and
byte length match the original archive. The guided publisher discovers this
receipt; the returned URL also works with the explicit human `prepare` command.
Source delivery alone does not verify dependency closure, sign provenance,
publish images or enable organization compute.

## Optional explicit human review

The configured source URL remains query-free and credential-free. GitHub's
stable `/releases/download/` URL may make one anonymous redirect to its exact
`release-assets.githubusercontent.com` release-asset path, including a transient
CDN query. Other redirects, login cookies, caller authentication and proxy
credentials are refused. Downloads retain the reviewed hash/size bounds and a
30-minute total transfer allowance.

Prepare a private review directory using the clean recipe checkout, the exact
retained OCI archive, the actual corresponding-source tar bundle, and its stable
public HTTPS delivery URL:

```sh
uv run python -m reasoning_ledger.image_review prepare \
  --source-root /private/reviewed-recipe \
  --archive /private/candidate/research-cpu.oci.tar \
  --profile research-cpu --repository ghcr.io/OWNER/REPO/research-cpu \
  --source-bundle /private/sources.tar \
  --source-url https://sources.example.org/immutable-sources.tar \
  --state /private/review
```

The destination repository must be lowercase. The draft contains actual file
hashes and installed SPDX package identifiers, not inferred source compliance.
Edit `review-draft.json`: identify the human reviewer, examine the full installed
dependency closure, and complete every component's disposition, corresponding
source paths, notice paths and rationale. Add records for dependencies omitted
from the observed inventory. Keep all three approval fields `false`.

Sign the reviewed draft interactively:

```sh
uv run python -m reasoning_ledger.image_review sign \
  --source-root /private/reviewed-recipe \
  --archive /private/candidate/research-cpu.oci.tar \
  --source-bundle /private/sources.tar --state /private/review \
  --private-key /private/review/maintainer-private.pem \
  --trusted-key /private/review/maintainer-public.pem
```

The wizard rechecks the retained archive, recipe, source inventory and coverage
before collecting three separate human confirmations. It creates a signing key
only after explicit key-creation consent, requires a nonempty confirmed
passphrase, and separately confirms enrollment of a new public key. Existing
keys must match the independently selected public key. The private key remains
owner-only and encrypted; never commit it. Signing does not publish anything or
produce an approved catalog.

Use `reasoning_ledger.image_publication` to publish that same retained archive
after its signed review and source-delivery checks. Do not rebuild an image after
reviewing its digest. A publication retry requires the original byte-identical
archive and inputs, repeats anonymous delivery and worker execution, and retains
separate bounded acceptance directories rather than overwriting their private
credentials. The successful returned execution report is validated and projected
onto `public-acceptance.json` outside those directories. Its fixed public fields
exclude enrollment credentials and provider headers. `publication.json` binds
that filename and SHA-256; completed retries preserve the original successful
public receipt while retaining additional private execution attempts.

After individual publications complete, combine their catalogs with fresh
anonymous source, registry-digest, pull and real worker-execution checks:

```sh
uv run python -m reasoning_ledger.image_review combine \
  --publication /private/published-research \
  --publication /private/published-lean \
  --trusted-key /private/review/maintainer-public.pem \
  --output /private/compute-images.json
```

Candidate catalogs, incomplete or altered execution receipts, altered signatures and duplicate
profiles are refused. No combined catalog is written unless every selected
publication passes. Review and commit that completed catalog at
`images/compute-images.json` for automatic release delivery. Only public
completion receipts and signed review inputs belong in publication artifacts;
the full acceptance directories contain enrollment credentials.

Signatures authenticate the selected attestation and enrolled key. Format 1
records a named human review; format 2 records machine-observed provenance with
explicit assurance limitations. Neither certifies an independent legal audit,
an exhaustive inventory, or an OCI image signature.
